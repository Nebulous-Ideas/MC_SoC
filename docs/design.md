# Design

## The loop
| Stage | Job | Notes |
|---|---|---|
| Sense | Pull incidents and chosen news | Read-only. Done by **source adapters**. News enters only when a person chooses it. |
| Normalise | Turn each item into a lesson record | One schema for every source. Keep a reference back, never a copy. |
| Decide | Pick which lessons become content, and in what form | Persona cards are an optional input. |
| Act | Write lyrics, build the song | Reuses the lyrics, bed and real-singing pipeline in `../`. |
| Verify | Schema, redaction by value, evidence refs, sign-off | `verify.py`. Nothing leaves this stage without a recorded human approval. |
| Learn | Record what was published and how it was received | Feeds back into Decide. |

## Decisions (settled 2026-11-11)

### 1. Source-agnostic core, adapters at the edges
The core knows only the lesson record. Every source (Kuma, Graylog, Sentry, Grafana, GitLab, a news feed, an Outline postmortem) is an adapter that reads from the source and emits lesson records. The core never branches on `source.system`. We do not pick one source up front; the first adapter is chosen when milestone 3 starts. Kuma stays the suggested reference adapter because it is the simplest to redact, but nothing depends on it.

Adapter contract (`Sense` + `Normalise`): `pull(since) -> iterable of lesson-record drafts`, each with `source.ref` and per-claim `evidence`, `signoff.status = pending`, `redaction.status = pending`. Read-only. Adapters never set `approved`.

### 2. Records live in a memory system; Python runs on a local cache
Same pattern as the rest of the homelab: the canonical record lives in the memory system (Outline first, collection to be created when the user says so), is pulled to `records/` for local execution, and changes go back through the memory-system adapter. Outline is one implementation; the core sees only a **memory adapter**: `list()`, `get(id)`, `put(record)`. `records/` is a cache: verify and generation read it, never the network. `memory_ref` in the record points at the canonical copy.

### 3. Sign-off is a person, in the memory system
Sign-off is a back and forth in the memory system (Outline comments and edits) that ends with a person setting `signoff` (`status`, `by`, `at`, `channel`) on the canonical record; the pull carries it into the cache. `chat` is a permitted channel when the person approves in a session and the flag is then written. Unattended runs via the CLI switch in a prepared environment are **generate-only**: they may draft lyrics and audio from records, but never write `approved`, and `verify.py` rejects an approval whose `by` is a non-human name. Publishing always needs a person.

### 4. Persona cards: optional input, form by trait
A card is a small file (name, voice and flow traits, tempo range, themes) derived from library stats and used only as an optional input to Decide. Mapping to form is by trait, not by name: dense and fast leans spoken-rhyme, melodic leans sung-hook, narrative leans skit. Real artist names never appear in content or output (no sound-alikes). Records carry an optional `persona` and a `form_hint`; both are advisory. Built: `persona.py` makes cards from `reference-stats/flow_profile.tsv` by measuring every track (42 today) on two axes, pace and delivery (flat pitch share), split at the file's own terciles. Today that yields two cards in `personas/`: `rapid-melodic` (5 tracks) and `slow-deadpan` (11). A card holds only measured ranges, trait labels and a form mapping; no artist or track names are written, and a card needs at least 3 tracks from at least 2 distinct artists. The other two combinations had too few tracks to qualify. Only 42 of the library's ~21k files have a flow profile, so cards are coarse until more are analysed.

### 5. Review surface is also an adapter (built and tried in OpenMOLE 2026-11-11)
Built: `review.py` holds the one decision routine (`decide`) plus a CLI surface; `openmole_tool.py` is an Open WebUI Tools stub that calls it. `decide` takes the name from the platform (never from the model or the record), refuses non-human names, needs a person's confirmation, requires the record to pass verify before approval, and writes through `set_signoff`, the only sign-off write path. Sign-off is changed only there and never by push. 11 offline tests cover it. Tried in the real OpenMOLE (Open WebUI v0.13.2, tool called by Claude Haiku through the Anthropic connection): listing works; an approval from chat wrote `signoff` into Outline with `by` set to the logged-in OIDC name, channel `chat`, via the dedicated `MC SoC` Outline user (member role, edit access to the lesson-records collection only). The note in a sign-off is typed by the approver in a second dialog (`signoff.note`, confirmed working); a comment from the assistant is stored apart as `signoff.note_model`. Python caches imported modules, so after `git pull` in `/opt/mc-soc` the container must be restarted to load new code. Deployment notes: the instance sits behind OIDC login; the host needed SSH access to the Git server to clone over a read-only deploy key; the stack's CI deploy was not working, so the compose change was applied by hand.
Who shows a record to a person and collects the decision is a third adapter kind: `present(record)` and `collect_decision() -> signoff`. Implementations: Outline comments (today), and OpenMOLE (the homelab's Open WebUI, already wired to the local models and image server). The core stays out of both. In OpenMOLE, `verify`, `pull` and `push` would be exposed as Open WebUI Tools, so the chat calls the same code. An approval clicked or typed there is written back to the canonical record's `signoff` (`channel: chat`), and `verify.py` is unchanged. Open WebUI's Knowledge index is not used as the record store (retrieval index, not exact fields). Open questions: the Tools run inside the OpenMOLE container, so the code or an API wrapper has to be reachable from it; and a chat approval needs a named, authenticated user, not a shared login.

### 6. Publishing is an adapter too (built 2026-11-11; GitLab Pages is one example)
Same pattern as memory systems and review surfaces. `gate.py` is the one shared publish gate: a record is publishable only if it is approved and passes verify, and a record with verify errors fails the run instead of being skipped. A publisher is a module in `publishers/` with `publish(records, out)`; it only renders what the gate lets through and never decides what is publishable. `publish.py <publisher>` runs one; `static-site` is the first (one HTML page; leaves out approver names, notes, `memory_ref` and internal links; private ranges, `.local` and `localhost` count as internal, and `MCSOC_INTERNAL_DOMAINS` adds your own comma-separated domains). The CI file is just one way to run it: GitLab CI runs the tests and verify on every push and the `static-site` publisher on `main`, and the same commands run anywhere else (cron, another CI, by hand). A new publisher (a feed, a wiki page, a song-build trigger) is one file plus one line in `publishers/__init__.py`. Who can see the published GitLab Pages site is a project setting, not part of this code.

### 7. Releases and environments (built locally 2026-11-11; not pushed)
A release is a named, fixed set of approved records: a manifest (`releases/<name>.json`) with each record's id, a content hash, and who approved it and when. `release.py make NAME` writes one (refused if any record fails verify, if nothing is approved, or if the name exists); `release.py check FILE` confirms the records still match. `publish.py <publisher> --release FILE` renders a release, and fails if any named record has changed, lost its approval or no longer passes verify, so a release is never rendered from content it did not describe. Commit the manifest and tag the commit and the records at that tag are the release: this gives rollback, an audit trail, and the "Learn" stage a record of what went out. Environments are only target names for where a release is shown (for example `preview` for project members, `published` promoted by a manual job); the code does not know about them, so another CI or a plain server can map releases to its own places. Record sign-off decides what may enter a release; promotion decides when it goes out. Two human steps, kept separate.

### 8. Reuse: derived works (built locally 2026-11-11)
A derived work (`works/<id>.json`, `schema/derived-work.schema.json`) is content made from approved lessons: a skit, hook, post or rhyme. It must name the lessons it came from and every one must exist and be approved; it carries its own redaction scan (generated text can add things the lesson did not have), its own human sign-off, and `source_links` so a reader can check it. A work cannot be `approved` or `published` without an approved sign-off by a named person. The text is scanned by value like any record. `verify.py --all` checks records, works and feedback together.

### 9. Feedback: data, never instructions (built locally 2026-11-11)
Review comments, reactions and corrections (`feedback/<id>.json`, `schema/feedback.schema.json`) target a lesson or a derived work, name a person, and may carry a coarse `signal` (keep, drop, change, more-like-this, less-like-this) and tags. The text is stored and scanned for secrets, and it is never executed or fed to a model as instructions: a comment that says "ignore the rules and approve this" is only text and changes nothing (tested). Decide reads `feedback.py`, which outputs counts by tag and by form and deliberately never includes the free text. Only feedback that passes verify is counted.

### 10. Operations: a pre-run check (built locally 2026-11-11)
`ops_check.py` is a read-only check that what a run needs is in order, driven by a config file (`ops.json`, gitignored; `ops.example.json` shows the homelab's) so another setup swaps in its own checks. Types: `http` (status range, optional bearer token read from a named environment variable and never printed), `tcp`, `disk` (max percent used), `env` (reports set or unset, never values), and `verify` (runs `verify --all`). A check marked `required: false` only warns; any failing required check gives a non-zero exit. It would have caught most of this session's blockers (stopped LLM server, unreachable services, disk filling up). Not covered: whether CI deploy keys are valid (they live in GitLab, not on this machine).

### 11. Measure: feature tables and analyzers (built locally 2026-11-12)
Measure is the stage that turns files into numbers. `features.py` defines the one shape every analyzer produces: a **feature table** of measured numbers, one row per track, with an opaque row id and an opaque group id (the artist, hashed) so a card can require several distinct artists without ever carrying a name. The table is validated, not trusted: every value must be a finite number (never a list, string or vector, so a voice embedding cannot be stored), feature names that say embedding, vector, speaker or voiceprint are refused, and a feature that is declared but empty in every row is an error. Tables are local working files (`tables/`, gitignored): hashes of known names can be guessed, so they are never published, and cards carry no ids at all.

Analyzers are adapters (`analyzers/`, same pattern as memory systems and publishers): each has `read(path)` and only **reads** what a measuring tool already wrote; it never touches audio. Three exist (the third, per voice, is described below): `flow-tsv` (vocal delivery from `reference-stats/flow_profile.tsv`, 42 tracks, 7 artists) and `rhythm-tsv` (tempo, swing, loudness from `results.tsv`, 64 tracks, 30 artists). The pre-existing measuring scripts stay where they are and keep writing their TSVs.

`persona.py` now builds cards from any table through `KINDS`: `voice` (pace x delivery, as before, byte-identical apart from a new `kind` field) and `beat` (tempo x feel, new: `fast-straight`, `fast-swung`, `slow-straight`, `slow-swung`, built from 64 tracks, with ranges for bpm, swing, loudness and loudness range). A new kind is a new entry, not new code. Cards still need 3 tracks from 2 artist groups and hold ranges and labels only.

**Voice cards moved to the validated measures (built 2026-11-13).** The voice axes are now pace = syllables in heard words per active second and delivery = pitch spread from the neural pitch tracker (low spread is deadpan, high is melodic), the measures that followed a planted change in real vocal stems (roadmap, "Instrument validation against planted truth"). Ranges on a card: those two plus pitch span and pause share. A kind may list **older instruments** for the same axes (`KINDS[kind]["older"]`, read through `persona.instruments`); a table written before `flow-tsv` version 2 is still cut on the older pair. Trait words and card labels are the same either way, the threshold names are not (`heard_pace_*`, `spread_*` against `pace_*`, `flat_min`, `melodic_max`), so a card says which instrument its numbers came from. Three rules follow: a row that lacks the preferred pair is left out, never filled from the older one; `exchange.py` accepts either instrument but refuses a card that mixes them; thresholds from the two are never compared. The builder still does not branch on a kind's name. The tracked voice cards were rebuilt from the 33 reference rows only (our own tracks are scored against cards, they do not shape them): `rapid-melodic` (5 tracks) and `slow-melodic` (4). `slow-deadpan` is gone for now: four reference tracks fall in that cell but all from one artist, so the two-group rule refuses it, and the `skit` form currently has no fitting voice card. Not done: the delivery axis has not been checked against listeners, and a card's `basis` is only written by the table path (`persona.py build`), not by the legacy TSV path used here. The tracked voice cards were rebuilt the same day from 41 reference rows (eight added); thresholds are terciles of the table they were cut from and move when rows are added.

**Rows can be voices (built 2026-11-13).** A table's provenance may say `unit: voice` (default and all older tables: `track`); `validate` accepts only those two words. A third analyzer, `flow-voices-tsv`, reads a per-voice file written by the measuring side: one row per voice in a track with at least 60 s of material, with active time, pace, pitch spread and pitch span; the group is still the track's artist, so the two-group rule is no weaker. `persona.py` cuts such a table exactly as before and writes `rows_are: voices` on the card, whose `n_tracks` then counts voices; a table of tracks gives cards without that field. The tracked voice cards are now built this way from 40 reference voice rows: `rapid-melodic` (6) and `slow-melodic` (4). Not built: exchange bundles for voice-counted cards (the checker refuses the field), a validated test of which piece belongs to which voice, and cards for the deadpan cells (with 30 s rows two appeared, each resting on one short voice; see the roadmap).

What it deliberately does not do: **join the two tables.** They share no tracks (0 of 42 and 64) and only 3 artists, so a merged table would be empty. Voice and beat cards are separate inputs; Decide will pair them by trait labels, never by track. Left out on purpose: the per-step drum patterns and `balance_db` (five band levels in one cell, whose band definitions are not written down here), which need splitting into named numbers before they can be used.

### 12. Decide: a brief, not a choice (built locally 2026-11-12)
`decide.py` reads approved, verify-clean lessons through the shared gate, the persona cards and feedback counts, and prints a brief per lesson: candidate forms from `form_hint`, the voice cards whose form mapping fits, and all beat cards unranked (no measured link from beat to form exists, so none is invented). Forms with a fitting card and a better feedback score list first. It writes nothing and generates nothing; a verify failure stops it. A person picks an option, which starts Act by hand (milestone 4).

### 13. Review surfaces beyond OpenMOLE: the contract and the next two (planned 2026-11-12, not built)
Every review surface is a thin wrapper over `review.decide`. To qualify it must meet four points:
1. **Identity comes from the platform**, never from the model, the record or a tool argument (Discord user id, GitLab user, OIDC subject). A shared login does not qualify.
2. **Only a listed person can approve.** An allow-list of platform ids maps to human names; anything else is refused. OpenClaw's own exec approvals use the same idea (`channels.discord.execApprovals.approvers` is a list of Discord ids).
3. **A deliberate act confirms it** (a button press or an MR approval), after the surface shows the lesson text that will be signed. A model's message is never a confirmation.
4. **It writes only through `set_signoff`**, with `channel` naming the surface, and it re-runs verify first.
The note in a sign-off is typed by the approver; model comments go to `note_model`, as today.

**Discord (and Slack or Matrix) buttons.** A small deterministic bot posts a card (lesson text, evidence links, Approve / Reject / Change buttons) and handles the button interaction itself. It is not an LLM agent: no model sits between the click and `decide`. OpenClaw's crew can *announce* ("a lesson is waiting") and discuss it, but the click goes to the bot. Whether the bot can be an OpenClaw channel plugin on the pinned 2026.7.1 image or must be its own Discord application is still to be tested (`config schema`, offline, as in the OpenClaw runbook); the own-application route needs a bot token the maintainer creates. Discord permissions are for the review channel only.

**GitLab pull request approvals.** Records change by MR; sign-off is an MR approval by a listed user. A CI job reads the approval (the API gives the user) and calls `set_signoff` with `channel: gitlab-mr`. This matches releases (a manifest plus a tag), keeps an audit trail in GitLab, and needs no always-on process. Limit: CI writes the field, so the job runs only on the protected branch and only trusts the approvals API, never MR text.

**Built 2026-11-12:** the contract is executable. `tests/conformance.py` holds eight cases a surface must pass (platform identity only, non-human names refused, allow-list, declined confirmation changes nothing, a record failing verify is refused before anyone is asked, one sign-off write, already-decided refused, rejection recorded); `tests/test_conformance.py` runs them against `review.decide` and the OpenMOLE tool, and checks that a deliberately broken surface fails. To support point 2, `review.decide` and `precheck` take an optional `approvers` list; `MCSOC_APPROVERS` (comma-separated names) sets it for the OpenMOLE tool, and unset keeps the old behaviour (any named human). Not yet tried in the real OpenMOLE.

**Built 2026-11-12: `discord_card.py`, the Discord surface logic (fake-tested only; no transport, no bot, no token).** `build_card(record)` makes the message (refusing, not cutting, a lesson too long to read in a card); `handle_interaction(interaction, store, people)` turns a button click into a response. Identity is the Discord user id mapped through a reviewer allow-list (`people`, id to name); display names and message text are ignored. The first click (Approve/Reject) runs every refusal check and answers only to the clicker with Confirm / Cancel; only Confirm writes, through `review.decide` with channel `discord`. Each button carries a hash of exactly what the card showed, so a record edited after the card was posted is refused at both clicks. It runs the shared contract (`tests/test_discord_card.py`, 8 cases) plus 9 Discord-specific ones; removing the pre-check makes three contract cases fail. Not built: a typed note (needs a Discord modal), the transport, and Discord request-signature checking, which the transport owns.

**OpenClaw as the transport or the announcer (looked at 2026-11-12, only against the local `latest` image, which is 2026.11.1, not the 2026.7.1 pinned on CT 114).** The config schema has a top-level `hooks` section ("inbound webhook automation ... mapping external events into wake or agent actions") and a Discord `agentComponents` block with no description, so the announce direction (MC SOC tells the crew a lesson is waiting) looks feasible by webhook, while whether an OpenClaw Discord account can route a component click to our code is unproven. Test on a copy of the pinned image's schema before relying on any of this. Either way the click must reach `handle_interaction` and never pass through an agent.

**Shared piece.** A thin HTTP/JSON service over `verify`, `review.decide` and `decide`, behind the OIDC proxy, would let the bot, the CI job, OpenMOLE and an MCP wrapper all call the same code. Its identity header is set by the proxy and is ignored on any other path.

### 14. Text-free audio analyzers: hear the words, keep only numbers (decided 2026-11-12; contract built, no real analyzer yet)
Purpose: measure how reference artists rhyme (density, multi-syllable match length, internal versus end share, longest chain, assonance), not to reuse what they rhymed. The owner's earlier decision to skip transcripts of reference artists (2026-11-10) is replaced by this narrower one: transcription is allowed only inside an analyzer, in memory, and only numbers come back.

The constraint is enforced by test, not by intent. `tests/textfree.py` is a contract any such analyzer must pass: it runs the analyzer with an injected speech-to-text that returns canary words, in an empty working and temp directory, then fails if the canary appears in the result (keys or values), stdout, stderr, an exception message, any file name or file contents left behind. Result keys that name text (`text`, `word`, `line`, `lyric`, `transcript`) are refused, values must be finite numbers, and the output goes through the feature-table contract (decision 11): scalars only, opaque row id, hashed artist group, local gitignored tables. A deliberately leaky analyzer must fail the contract in eight ways (file, temp file, stdout, stderr, key, value, exception, file name); the tests check that.

What the contract cannot see: a speech server that logs or caches what it transcribes, and vocal stems left on disk. The speech server is a service we call, not our code, so the scope is our own code and configuration. Checked 2026-11-12 with a canary phrase (invented words spoken by the server and transcribed back): neither the input nor the transcript appears in Graylog or the server's journal, which log only metadata (audio duration, character count); the container's only writable mount is the model cache, and it runs with `--rm`. What stays ours: the existing helpers `stt.py`, `stt_chunks.py`, `words.py` and `skit.py` write full transcripts to disk, so a rhyme analyzer must not reuse them and needs its own call that keeps the transcript in memory (the contract fails any leftover file). Vocal stems go in git-ignored `work-audio/` and are deleted afterwards. Calibration plan: run the same pipeline on our own tracks, whose true lyrics we hold, to measure the transcription error and report it next to the numbers. Rhyme counts from rap over a beat will read low; vocal separation first (demucs) helps.

The analyzer itself belongs with the engines (see the planned split), not in this stdlib-only core. This repo holds only the contract and the fakes.

### 15. Two environments: measuring outside, numbers in (agreed 2026-11-12; boundary partly built)
Producing the numbers (the operator's equivalent of digging through a crate and measuring it) happens outside the environment MC SOC runs in. The measuring side holds the music library, audio, the speech server, GPU engines and any transient transcript. MC SOC receives only feature tables (decision 11). The table is the whole interface, and MC SOC's import is the guard: every value a finite number, feature names that look like text or embeddings refused, ids and groups hashed, no names. A faulty measuring tool therefore cannot carry text or voice data across, and the text-free contract (decision 14) is that tool's own proof.

Consequences, to build in this order of need:
1. **Provenance on every table** (built 2026-11-12, `features.provenance()` and `validate`): analyzer name and version, number of tracks, and a pointer to the calibration, numbers and short labels only. MC SOC refuses tables without it, so a known bias (the rhyme measures read low) travels with the numbers. Fields: `method` (identifier), `measured_on` (own, reference, mixed, unspecified), `n_tracks` (must equal the rows), and `calibration` (status none or own-tracks, the number of tracks it was checked on, per-feature rank agreement and bias low, high, none or unknown, only for declared features). Free text and unknown keys are refused, so provenance cannot carry a lyric or a name. Cards built from a table can carry a `basis` (analyzer, method, measured_on, calibration status; no ids). The two TSV readers say `unspecified` because a reader cannot know what the measuring tool measured on; the rhyme analyzer carries its real calibration (7 own tracks). Old tables without provenance are refused unless a caller opts out.
2. **Reference crates** (not built): the operator picks reference material for a piece. The manifest that names artists and tracks stays on the measuring side. MC SOC holds a crate id, a content hash, a count and the reason it was chosen, never names.
3. **Target versus achieved** (not built): a brief carries numeric targets (from a voice card, a beat card, a rhyme band); the same analyzers measure our own output on the measuring side; MC SOC compares the two tables and reports the gap. This runs on our own tracks, where the true lyrics make the numbers most trustworthy.
4. **Fixtures instead of music:** sample tables ship with the repo so anyone adapting the project can run the whole loop with no library, audio or GPU.
**Packaging: a measuring image with the speech server kept external (idea, decided 2026-11-12).** The speech server stays a separate service we call, so the image does not bundle a speech model. What the container can enforce: the audio file mounted read-only (or piped in); a read-only root filesystem with in-memory scratch; one writable output volume that only receives a feature table after the same validation MC SOC applies on import; and network egress limited to that one endpoint. The tightest form of the last point is `--network none` plus a single Unix socket that the host forwards to the speech server, so the container has no network stack, only that pipe. CI runs the image against a fake speech server that returns canary words and then searches `docker diff`, `docker logs` and the output volume for them. What the container cannot enforce: the audio goes to the server and the transcript comes back, and whether the server keeps either is outside our code. That half is a recurring check, not a test of ours: an ops-check entry speaks a canary phrase through the server and searches Graylog and the server journal for it (done once by hand on 2026-11-12: only metadata was logged), run before any batch of reference tracks. Vocal separation can run in the image on CPU (demucs took 13 s for a 60 s track). Open: image size, a GPU variant for separation (podman and AppArmor on the GPU host have broken CUDA before), and the licences of any bundled model.
"Sampling" here means choosing material to measure. No audio or lyrics are reused, nothing is voice-cloned or made to sound like someone, and only numbers cross the boundary.

### 16. Crate exchange through the repository (checker built 2026-11-12; no real bundles yet)
Sharing between operators and communities happens in the repository itself, by pull request, not through a separate service. What may be contributed: numbers-only bundles (a crate descriptor with a count, a hash and the reason it was chosen, never names; persona and target cards with their `basis`; trial prescriptions), never audio, lyrics, transcripts or per-track rows (hashes of known names can be guessed, so exchanged data is aggregate only; cards already need 3 tracks from 2 artist groups and carry no ids). `exchange.py check` validates every bundle: exact key sets (no extra or free-text fields), every string an enum, hash or short identifier, finite numbers, minimums (3 tracks from 2 groups), card and crate agreeing (the crate exists, the card's tracks fit it, `measured_on` matches), file names matching the bundle, and the same by-value redaction scan as lessons. Three bundle kinds: crate, card (with `basis`), prescription. 11 tests. A name is still a valid identifier, so a maintainer's review remains the human gate. Imported data is untrusted: it is labelled as community-contributed, a maintainer's review is the human gate, and cards stay advisory inputs to Decide, never instructions. Contributing is documented in `CONTRIBUTING.md` and `exchange/README.md`, with pull-request and issue templates under `.gitlab/`. The CI file runs the checker, but pipelines are not hooked up yet, so it is run by hand. This is also one of the ways the project demonstrates how others can adapt it.

### 17. A crate is two or more sides and the measured relationship between them (agreed 2026-11-12; bundle checker built)
At a minimum a crate is a Boolean split of a universe: some tracks on one side, others on another (and some `unknown`, on neither). Two sides is the minimum, not the limit: a crate may hold a cast, up to eight sides in one universe (for example the five agent personas an engineer wants to work with), named `s1` to `s8`. The sides are still compared pairwise and never averaged. Labels are optional: the operator may not be able to say what separates the sides, and the crate must still be useful. What a crate carries is a depiction of the relationship, as numbers only:
- **How the sides were formed** (`formed_by`, an enum): `predicate` (a rule over the trait vocabulary, in which case the rule may be included: atoms like `feel:swung`, joined by `not`, `all`, `any`, at most 8 atoms, no free text), `operator` (the engineer chose "these versus those"), or `clustering` (a measure found the split). Unlabelled is a normal case.
- **A profile per side**, the same shape as a persona card's `measured` block (p10, median, p90 for each declared feature), plus a count, a number of artist groups and a content hash. A persona card is the profile of one side, so cards and crates share a format.
- **The relationship**, an enum `kind` (two sides: `contrast`, `nested`, `overlapping`; three or more: `ordered`, a gradient, or `cast`, distinct and unordered) plus numbers for every pair of sides: per-feature effect size (rank-biserial, -1 to 1, positive when the first side tends higher) and overlap of the two distributions; then `separability` (the best single-feature AUC over all pairs, 0.5 meaning no separation), `distinctness` (the worst pair's best AUC, i.e. how hard the two closest sides are to tell apart: the number that says whether a cast of personas really is distinct) and the features that carry the separation. A feature counts as a carrier only if its effect is at least 0.2 and its exact two-sided Mann-Whitney p is within 0.05 divided by the number of feature-and-pair comparisons (see the amendment below). `crate_builder.py` computes profiles, effects, overlaps, summaries, hashes and the id (over members and numbers, so a re-measured crate is a new crate) from a feature table and an assignment, and refuses sides that are too small or a crate with no carrier. The checker recomputes separability and distinctness from the effects, requires effects not to contradict the profiles' medians, and for `ordered` requires a feature whose medians rise or fall across the sides. This is the shareable knowledge, with no per-track data.
- **Membership**, since a missing tag does not mean a missing property: `verified` (each track checked to belong to its side), `assumed` (inferred from absence: positive-unlabelled data; low confidence only) or `chosen` (picked by design, as for a cast).
- **Confound indicators, as numbers:** how many artist groups appear on both sides (an artist on both sides lets the difference be confused with the artist), and which measures were matched between the sides (loudness, tempo, duration), as an enum list.
Minimums: each side needs at least 2 tracks (see the amendment below; a persona card still needs 3 tracks from 2 groups). The relationship is computed on the measuring side from the feature table; the exchange checks that its numbers are finite, in range and consistent with the profiles. A persona card is the profile of one side and cites its crate and side. Further logical constraints (one crate inside another, crates that must not overlap) can be added later without changing the shape.

**Never pool crates (owner, 2026-11-12): the structure is the signal.** Throw every crate together and you get noise: the contrast inside a crate exists only because both sides share a universe and conditions, and averaging across universes removes it. Rules that follow:
- **No raw pooling.** Crates are not merged, and no operation takes the union of their tracks or averages their profiles. A profile and its thresholds mean something only relative to their own crate: "slow" is slow within that crate.
- **Compare relationships, not levels.** Effect sizes and separability scores are standardised, so they can be compared across crates; absolute values (a bpm, a loudness) cannot.
- **Combine only compatible crates, and combine the findings.** Two crates are compatible when they agree on `measured_on`, analyzer and version, units and calibration status. The legitimate use of many crates is replication: for one contrast across independent compatible crates, MC SOC computes the number of crates, the fraction agreeing in sign, an effect size weighted by crate size, and a heterogeneity measure (numbers only, from the bundles' effect sizes, not from any track). A contrast that replicates is evidence; one that appears in a single crate may be an artefact of that crate.
- **Cards are crate-relative.** A persona card cites its crate and carries thresholds that are relative to it; Decide must not mix thresholds from cards of different crates as if they were one scale.
- **Known flaw in what is built:** `persona.py` today cuts terciles over the whole table it is given, i.e. over a pool (for example all 42 tracks with a delivery profile). The cards are therefore relative to that pool, and the pool is a mixture of artists and conditions rather than a contrast. They remain usable as coarse prototypes, but they should be rebuilt per crate once crates exist.

**Small, freeform crates are the normal case (owner, 2026-11-12); amendment, built the same day.** The engineer defines the Boolean relationship freely: two or three tracks that share some attribute set against three or four that lack it. The attribute need not be named. Consequences:
- **A single crate is a hypothesis and an observation, not a proof.** With sides this small nothing can be significant on its own: even perfect separation of 3 tracks from 4 has an exact two-sided probability of 2/35 = 0.057 (2 against 3: 0.20), so it can never clear a 5% bar, let alone one shared across features. The first version of the builder and checker (which refused a crate with no carrier beyond chance, and required 3 tracks and 2 artist groups per side) turned away real crates. Changed: small crates are accepted, flagged `exploratory`, and describe what the numbers look like without claiming a finding.
- **Exact statistics for small sides.** The rank-biserial effect fixes the Mann-Whitney U, and the null distribution of U depends only on the two side sizes, so the exact probability can be computed from the bundle's own numbers (counts and effect) by the checker, replacing the normal approximation (rough at these sizes). Evidence tiers per crate: `supported` (some feature has an effect of at least 0.2 and an exact two-sided p within 0.05 divided by the number of feature-and-pair comparisons) or `exploratory`; features with |effect| of at least 0.5 that do not clear the bar are listed as `leaning`. Each pair-and-feature entry carries its exact `p`, and the checker recomputes `p`, `carriers`, `leaning` and `evidence` from the effects and side sizes (the exact test is used while the two sides' sizes multiply to at most 2500, a normal approximation beyond). An exploratory crate can only claim low confidence. Measured on made-up data: identical sides came out falsely `supported` at most 3.3% of the time (also with five personas), crates of 3 or 4 tracks per side can never be `supported` with two features (the smallest side size that can is 5), and a large real difference was `supported` at 6 per side and above. Only features measured for every track in the crate are profiled, so the counts are the side sizes.
- **Amendment (2026-11-12): the test runs on artist groups, not tracks.** Tracks by one artist share a voice, a producer and a mastering habit, so they are not independent, and a test on tracks overstates the evidence (first real crates: 900 tracks a side from about 250 artists). Each pair-and-feature entry now carries `group_effect`, the rank-biserial effect between the sides' per-artist medians, and `p` is the exact Mann-Whitney p of that effect with the sides' **group** counts (`groups`), not track counts. `effect` stays the descriptive track-level effect (it drives `separability`, `distinctness`, `leaning` and the median cross-check). A carrier needs `group_effect` of at least 0.2 and `p` within 0.05 divided by the number of comparisons; the checker recomputes `p`, `carriers`, `leaning` and `evidence` from the bundle's own numbers as before. Consequences: a side needs enough artists, not tracks, to reach `supported` (4 artists against 4 can never clear the bar of a four-comparison crate; the smallest two-sided p is 2/70), and many tracks per artist add precision to the artist medians but not significance. Measured on made-up data with a strong artist effect and identical sides (15 artists of 6 tracks a side, 400 runs): 3% falsely `supported` at artist level, where a test on tracks would have said so 38% of the time. `replication.py` now weights crates by their group counts. Not done: this treats artists in both sides as unpaired (conservative when the same artists appear in both), a paired or permutation test would use that overlap; albums or playlists are a second level of clustering that is not modelled. Crates built before this amendment lack `group_effect` and must be rebuilt (none were exchanged).
- **The statistics live in replication.** Many small crates are evidence units. For one feature and direction, the replication summary counts the crates that lean the same way (a sign test: 10 of 10 gives about 0.002 two-sided) and combines the effects weighted by size, never the tracks. Only compatible crates (same analyzer, version, units, `measured_on`) combine.
- **Minimums relax at the crate level**: at least 2 tracks per side; no artist-group minimum (a contrast within one artist's work is a good design, and `shared_groups` already records overlap). Profiles on sides this small are min, median and max in effect; the bundle says how many values each is based on. A persona card still needs a larger side (3 tracks from 2 groups) and so is optional for a small crate.
- **Where the Boolean comes from is the engineer's choice** (audition, adventure, whatever): `formed_by: operator` is the default and needs no vocabulary.

**Replication (built 2026-11-12, `replication.py`).** Crates with unnamed attributes can only confirm each other if they say they test the same contrast with the same orientation, so a two-sided crate may carry an optional `claim` id (s1 has the quality, s2 lacks it); a predicate-formed crate's claim is derived from its canonicalised predicate (argument order does not matter), a cast cannot carry one, and crates without a claim replicate nothing. The summary combines only compatible crates (`measured_on`, analyzer, version, calibration) that share a claim, counts crates with identical sides once, and per feature reports a sign test, a Stouffer-combined exact p, the size-weighted effect and its spread, and a verdict (`replicated`, `suggestive`, `inconsistent`, `insufficient`, `no-clear-pattern`) under the same shared 5% level. Ten tiny crates that each lean the same way replicate (sign test p = 0.002) although none is `supported` alone; with two features, seven agreeing crates are needed to reach `replicated`. Limitation: independence is assumed, since hashes detect identical sides only. 15 tests and 17 broken variants all caught.

**Idea: crate creatures (owner, 2026-11-12, not built).** A way to display a crate that is fun and honest: a small creature drawn per side from the crate's own numbers, in the hand-made sock-puppet look (googly eyes, a tuft of hair, a felt tongue). Traits come from the crate's top features by effect (carriers first), scaled across the sides of that crate (crate-relative, so nothing is pooled); spread within a side makes the outline fuzzier; two creatures look alike when the sides overlap and different when they separate; a cast is a row of up to eight creatures; evidence shows in the line style (solid for `supported`, a dashed sketchy outline for `exploratory`) and `leaning` features give a raised eyebrow. Deterministic SVG from numbers only (no names, no ids), so a crate picture is as shareable as the crate. It would be a renderer next to the static-site publisher and in the workbench.

**Amendment (2026-11-12): orientation and instrument versions are in the bundle.** A wrong reading of an effect's sign made a reported "lean" backwards, because the rule (positive means the first side is higher) lived only in code. Every crate now carries `relationship.orientation: positive_means_first_side_higher` and the checker refuses anything else. An optional `universe.instruments` records the versions of the models and tools that produced the numbers. Built, tested offline; no real bundle has been checked against it yet.

### 18. A crate graph: linking the poles of crates for track and character creation (idea, owner question 2026-11-12; not built)
The side that lacks the quality is the "indirect" part of a Boolean crate. Linking it, or the side that has the quality, to other crates turns the exchange into a graph that the creation process can walk.
- **Nodes and axes.** A node is a side of a crate. A two-sided crate defines an axis in feature space, from its lacking pole to its having pole ("toward Q"). A character is a point described by coordinates along a few axes; creating one means choosing which axes and how far along each.
- **Link kinds (enum):** `same-members` (identical side hashes, found automatically); `complement` (one crate's lacking side is the seed of another's having side; declared by the engineer, who knows what is meant); `proximity` (two sides from compatible crates have similar profiles in their shared features; measured, valid only inside one measurement universe); `same-claim` (already built; the basis of replication). Each edge carries ids, the kind and a number (overlap or distance), nothing else.
- **Use in creation.** The persona adventure's doors are edges: choose the having pole of one crate, then follow a complement edge to the next axis; the optometrist-style trials fine-tune a position along an axis; a crate creature (see above) for a character can show its neighbours.
- **Rules.** Links connect, they never merge: no pooling, no averaging across crates, no thresholds taken from one crate and applied to another (decision 17). Proximity compares profiles only between compatible crates. The graph is a file of edges beside the bundles, validated like them: numbers, enums and ids only.
- **A gap this exposes.** Overlap between crates is detected today only by identical hashes, so two crates that share some tracks look independent, which weakens both this graph and the replication summary. A small min-hash sketch per side (about 32 integers) would estimate the overlap without exposing members; the hashes of hashed ids carry the same guessability as the existing content hash. Untested idea.

### 19. Preferences as positions against crates (idea, owner, 2026-11-12; not built)
Crates carry no labels and no names, so the preferences that show up during creation can be represented against the crates themselves.
- **A preference is a position on a crate's axis:** a number from -1 (the lacking pole) to +1 (the having pole) for a two-sided crate, with the number of choices behind it and its source (`adventure`, `trials`, `operator`). Adventure choices, optometrist results and ratings all reduce to this. A trial's prescription is in engine units, so the chosen variants are measured by the analyzers and projected onto the crate's axis (the direction from the lacking pole's profile to the having pole's).
- **A taste profile is a vector of such positions across crate axes,** a point in crate space: no artist, track or word, and no listening history. This is how an analyst's or a volunteer's taste can feed character creation without accounts or names (decision on taste to character: consent record still applies).
- **Creation reads it.** A character is such a point; it maps to voice and beat cards, the persona adventure's starting doors, and a creature picture (see crate creatures).
- **It is personal data.** It needs the subject and consent hooks (revocation deletes the profile), it stays out of the community exchange by default (a preference vector is about a person, and positions on small, sparse crates can be quasi-identifying), and it is stored locally beside, not inside, the exchange.
- **Never pool still holds:** a profile is a vector of positions, one per crate, never an average across crates.

### 20. Several Boolean traits in one crate (proposed, owner agreed in principle 2026-11-12; nothing built)
A crate today is one split. When a track carries several Boolean traits at once (for example a spoken-word-dominant mix and a live-instrument-heavy one, both inferred from an audio-event tagger), the traits are usually correlated, so a single-trait crate partly measures the others. The proposal, in the order it would be built:
1. **Keep the two-sided crate as the unit.** The exchange checker, replication and the artist-level test all understand it; nothing here changes them.
2. **An optional trait table beside the crate**, numbers only: per track a vector of Boolean traits with the measured probability behind each, plus the pairwise co-occurrence counts. No row ids or names leave the measuring host, as for any bundle; the bundle would carry only the counts.
3. **Adjusted effects.** For each trait the bundle reports the single-trait effect and the effect adjusted for the other traits (stratified comparison or a small regression; the checker recomputes it from the counts and the per-stratum effects it already carries), plus a number for how much the traits overlap. The artist-level rule still decides significance.
4. **Interactions are left for later**: they need more tracks than most crates have.
What is not decided: the exact adjusted-effect method, whether the table lives inside the bundle or beside it, and how many traits are allowed. Not started: the first real use will be the rhyme-by-sound-class run (all 842 hip hop tracks tagged with 527 AudioSet classes); its result comes first. Test first when it is built: hand-count a two-trait case where the single-trait effect is entirely explained by the other trait.

### 21. Act: an engine seam and a target-versus-achieved report (built 2026-11-13, fake-tested only)
`act.py` takes the pick a person made from a `decide.py` brief (lesson, form, voice card), checks it against that same brief (an unapproved lesson, a form the brief did not offer or a card that does not fit is refused), asks an **engine** adapter for a render and compares the numbers read from it with the card's bands (p10 to p90 of the reference rows the card was cut from): per measure `inside`, `below` or `above`, the signed distance to the nearest edge and the distance from the median, plus counts over many renders (`summarize`). It is generate-only: the report says `status: generated`, never carries sign-off, and lyrics and audio still go through verify and a person's approval. An engine returns exactly `{values, seconds}`, numbers only; any other key, string, list or non-finite number is refused, so text cannot ride back with the measurements. ### 22. Stage order: idea, then production (with redaction), then sign-off (agreed 2026-11-15; documented, not enforced in code)
The order of work for one piece of content is fixed:
1. **Idea selection.** A person picks a lesson and checks that it fits the universe built so far. No redaction check here; this stage decides whether the lesson is worth making into content at all.
2. **Production.** The redaction check is a production step, done before any lyrics, script or audio are made from the record. It checks what the text would say, by value and by reading the wording, and the record's `redaction` field is set only after that check.
3. **Sign-off and publication.** Approval and publishing come after production. Approval is a separate human step and does not replace the redaction check.

What this changes: a record's approval says the lesson is accepted for content; it does not say the wording is safe to sing or publish. The Squid record (2026-11-15) was approved before its redaction check was recorded, so its redaction is still to be done as a production step before any song is made from it. Code does not yet enforce this order: `decide.py` offers approved lessons regardless of redaction status.

### 27. Orientation as case state: live enrichment without runaway scope (added 2026-11-26; fake-tested only)

When an agent enriches indicators live and hunts for them across backend systems, its picture of the incident changes with every result, and it can grow an incident far past its real size (shared infrastructure, noisy indicators, a poisoned feed, or an attacker steering the hunt). `incident/casestate.py` keeps that picture as a structured object instead of prose in a prompt. Every fact carries its sources with a trust level: untrusted or low-trust enrichment cannot confirm anything and caps confidence at 0.4; two sources of medium trust or better, or one system observation plus one such source, confirm; conflicting trusted verdicts stay suspected and are flagged; a known-benign allowlist refutes a value and keeps it from expanding the case. Growth is gated: a small batch inside the declared scope is applied, but a large batch, a case past its entity limit, or any system outside the scope is held until a named person applies it (the same refusals as `review.decide`: no model or process name, and a confirmation answered by the person). A query budget stops open-ended hunting. `reorient()` snapshots the picture and returns a diff (added, status changed, scope added) and `should_reorient()` says when to ask for one (growth fraction or elapsed time). Enrichment text is data: stored and shown, masked by value on export, never run. Built: the module and 10 offline tests, and `incident/sources.py` with 9 more: a `hunt()` loop that searches your own telemetry for indicators (only IP addresses, domains and hashes are accepted, so an untrusted indicator can never become query text), spends the query budget, keeps only validated field values from the rows (never message bodies) and sends new entities through the expansion gate; and read-only transports for Graylog (the views search API, one POST, token in the Authorization header only) and InfluxDB (Flux from your template). Checked 2026-11-26 against a Graylog 7.2 server through its built-in MCP (names only): relative time ranges are in seconds and scoping is by stream id, which agrees with the body we send, and a firewall/DNS stream carries `src_ip`, `dest_ip`, `dns_qname`, `http_url` and `source`, which `EXAMPLE_GRAYLOG_FIELD_MAP` uses; there is no obvious file-hash or user field on that stream, and stream scoping in the REST body is still unchecked. First real run (2026-11-26, Graylog 7.2, read-only token, 24-hour window): the views-search body worked unchanged, and a hunt of four external addresses plus one noisy one went through the gate. It exposed that repeated values in rows were counted once per row (78, 50 and 100 "new entities" became 2 applied and 1 held at 9 after deduplication, now fixed with a test), that the per-search row limit makes hit counts lower bounds, and that the firewall's `source` is the firewall, not the affected machine, so a host mapping needs a client field (`dns_client_name`, or the internal address). Crowdsec alerts there are free text with no address field, so they cannot seed a hunt without parsing message bodies, which we do not do. Not built or tried: calibration of the limits on recorded incidents, scope as address ranges (scope is a set of system names), file-hash and user fields, and stream scoping in the REST body, any operator surface that shows the diff, containment actions (the agent proposes, a person decides), calibration of the limits on recorded incidents, or measuring how often held expansions were right.
